# RescueSwarm: план исследования

Смешанный рой из дронов и наземных роботов совместно строит карту неизвестной
зоны бедствия и отмечает на ней места, где могут быть люди. Всё выполняется в
симуляции.

**Статус:** Фаза 0 завершена 2026-11-07: Docker-образ собран, Gazebo работает на
NVIDIA, замеры и видео готовы, см. [отчёт Фазы 0](PHASE_0_REPORT.md). Фаза 1
завершена 2026-11-07: 3 наземных робота с сенсорами управляются независимо, RTF
около 1.0, см. [отчёт Фазы 1](PHASE_1_REPORT.md). Фаза 2 завершена 2026-11-07:
3 робота без участия человека исследуют случайный мир (покрытие 95–96 % на 4 `seed`),
см. [отчёт Фазы 2](PHASE_2_REPORT.md). Фаза 3 (тепловизорная часть) завершена
2026-11-08: на 4 `seed` найдены 17 из 17 достижимых людей, ни одна ловушка не
подтверждена, см. [отчёт Фазы 3](PHASE_3_REPORT.md). Фаза 3b (YOLO по RGB и
модель Rescue Randy) завершена 2026-11-08: на 4 `seed` подтверждены 19 из 19
достижимых людей с RGB и без него, ловушек подтверждено 0, редкие призраки остаются
(1-3 на 4 `seed`), см. раздел «Фаза 3b»
в [отчёте Фазы 3](PHASE_3_REPORT.md). Фаза 4 завершена 2026-11-10: Фазы 2-3
работают на позе от `mrg_slam` (с нашей склейкой с колёсами и гироскопом), на 4 `seed`
подтверждены 19 из 19 достижимых людей, ловушек 0, ATE rmse 0.26 м; но точность карты
P@2 0.70 против 0.97 по истинной позе (порог 0.7 не пройден на 0.002, между прогонами
0.67-0.82), замыкания петель выключены, начальная поза известна, см.
[отчёт Фазы 4](PHASE_4_REPORT.md). Следующая Фаза 5.
Фрагменты конфигурации в разделе 7 остались черновиками: рабочие версии
лежат в `docker/` и `Makefile`, отличия перечислены в отчёте.

## 1. Цель

Исследование для портфолио Bekai Vision, которое позже может вырасти в продукт.

Итоговый результат:

- воспроизводимая симуляция, запускаемая одной командой;
- демо: рой исследует завал, спасатель видит общую карту и метки людей;
- технический отчёт с замерами;
- короткое видео после каждой фазы, которым можно поделиться в LinkedIn.

Исследование открытое. Закрытым позже может стать только продуктовый слой,
например GUI для спасателей.

**Целевой размер роя: 3–5 роботов.** Этого достаточно для исследования, и такой
рой должен работать на ноутбуке.

**Вне рамок сейчас:** реальное железо, рой больше 5 роботов, закрытый GUI,
сертификация, заявления о готовности к настоящим спасательным операциям.

### Исследовательские вопросы

1. **RQ1.** Насколько смешанный рой быстрее находит людей, чем только наземный
   или только воздушный?
2. **RQ2.** Как обрывы связи и ограниченная пропускная способность ухудшают
   покрытие, качество карты и поиск людей?
3. **RQ3.** Насколько точно совмещаются карты дрона и наземного робота, которые
   видят одно место с очень разных ракурсов?
4. **RQ4.** Как результаты меняются при росте роя с 3 до 5 роботов?

## 2. Docker или нативная установка

**Берём Docker. Опасение верное, но главная причина другая.**

ROS ставится в `/opt/ros/<дистрибутив>` и работает только после `source`, поэтому
сам по себе он систему обычно не ломает. Решающий аргумент на этой машине:

- на хосте Ubuntu 22.04 и ROS 2 Humble, который подключается в `.bashrc` и `.zshrc`;
- Humble поддерживается только до мая 2027;
- ROS 2 Jazzy рассчитан на Ubuntu 24.04, поэтому на хост нативно он не встанет;
- обновлять ОС ради проекта рискованно: на машине уже есть другие рабочие проекты;
- Docker закрепляет версии и делает эксперименты воспроизводимыми.

Цена Docker: нужно настроить графику, GPU и сеть. Существенной потери скорости
быть не должно: контейнер работает на ядре хоста, а GPU подключается напрямую.
Это проверим замером в Фазе 0.

## 4. Технологии

| Слой | Выбор | Почему |
| --- | --- | --- |
| Контейнер | Ubuntu 24.04 (`ros:jazzy`) | Целевая ОС для Jazzy |
| ROS | ROS 2 Jazzy, LTS до мая 2029 | Самая проверенная связка с нужными библиотеками |
| Симулятор | Gazebo Harmonic, LTS до сентября 2028 | Рекомендуемая пара для Jazzy |
| Дроны | PX4 SITL + модель на базе X500 | Реалистичный полётный стек |
| Связь с PX4 | uXRCE-DDS, один `MicroXRCEAgent` | Штатный способ |
| Навигация | Nav2 | Стандарт для ROS 2 |
| Совместный SLAM | `mrg_slam` (BSD-2) | Jazzy, Docker-образы, Gazebo-симуляция, 3D LiDAR |
| Запасной SLAM | Swarm-SLAM (MIT) | Децентрализованный, но версию ROS надо проверить |
| Исследование зон | Свой frontier + аукцион | Это ядро исследования |
| Детекция | Тепловизор + YOLO на RGB | Быстрый старт, тепловизор есть в Gazebo |
| Визуализация | RViz2, позже веб-интерфейс | Быстрый старт |

**Почему не Lyrical + Jetty.** Эта связка новее и поддерживается до 2031, но
требует Ubuntu 26.04, а PX4 и `mrg_slam` проверены на более старой базе. На неё
можно перейти, когда появится повод. Docker упростит переход.

**Лицензии.** Ultralytics YOLO распространяется под AGPL-3.0. Это подходит,
потому что исследовательский код будет открыт под совместимой лицензией. Закрытый
GUI делаем отдельным проектом: он не включает YOLO и работает с открытой частью
через сетевой API. Перед коммерческим запуском эту границу нужно проверить у юриста.

## 5. Архитектура

```text
Gazebo Harmonic (мир, физика, сенсоры, ground truth)
        │ ros_gz_bridge / PX4 uXRCE-DDS
        ▼
┌─ Робот N (ground_N или drone_N) ───────────────┐
│  Локальный SLAM ──► Локальная карта            │
│  Детектор людей ──► Кандидаты на карте         │
│  Распределение целей ──► Nav2 / PX4            │
└───────────────┬────────────────────────────────┘
                │ сжатые подкарты, метки, ставки
                ▼
        comms_sim: дальность, стены, полоса, потери
                │
                ▼
     Другие роботы и станция спасателя
```

Принципы:

- **Одна общая карта.** Дроны и наземные роботы дополняют одну карту, а не ведут
  отдельные. Дрон видит крыши и завалы сверху, наземный робот видит стены и
  проходы сбоку. Роботов нужно привести к общей системе координат. Сначала делаем
  это для наземных роботов, дроны подключаем в Фазе 5.
- **Децентрализация.** Каждый робот работает автономно при потере связи.
- **Единый контракт робота.** Логика роя не зависит от типа робота.
- **Разделение задач.** Дроны быстро осматривают зону, наземные роботы проверяют
  кандидатов вблизи и заходят в узкие места.
- **Роботы стартуют из одной зоны.** Это реалистично для спасателей и даёт
  начальное приближение для совмещения карт.
- **Обмен только через `comms_sim`.** Иначе DDS покажет все топики всем роботам,
  и результаты RQ2 будут недостоверны.

## 7. Фаза 0: установка и настройка

**Цель:** одна команда собирает образ, Gazebo работает на NVIDIA, окно открывается
на хосте.

### 7.1. Требования к хосту

Всё уже установлено. Команды только проверяют это:

```bash
docker run --rm --gpus all ubuntu:22.04 nvidia-smi
```

```bash
docker compose version
```

### 7.2. Черновик Dockerfile

Версии и digest базового образа закрепим при первой сборке.

```dockerfile
FROM ros:jazzy-ros-base AS base
ARG HOST_UID=1000
ARG HOST_GID=1000
RUN apt-get update && apt-get install -y \
      ros-jazzy-ros-gz \
      ros-jazzy-navigation2 ros-jazzy-nav2-bringup \
      ros-jazzy-rviz2 ros-jazzy-rmw-cyclonedds-cpp \
      python3-vcstool libegl1 libgl1 mesa-utils ffmpeg \
    && rm -rf /var/lib/apt/lists/*
RUN groupadd -g ${HOST_GID} dev && useradd -m -u ${HOST_UID} -g dev dev

FROM base AS dev
USER dev
WORKDIR /workspace
```

Этап PX4 добавим в Фазе 5, чтобы не увеличивать образ раньше времени.

### 7.3. Черновик compose.yaml

```yaml
services:
  dev:
    build:
      context: ..
      dockerfile: docker/Dockerfile
      target: dev
    image: rescueswarm-dev:jazzy
    runtime: nvidia
    network_mode: host
    ipc: host
    environment:
      - DISPLAY
      - XAUTHORITY=/tmp/.docker.xauth
      - NVIDIA_VISIBLE_DEVICES=all
      - NVIDIA_DRIVER_CAPABILITIES=all
      - __NV_PRIME_RENDER_OFFLOAD=1
      - __GLX_VENDOR_LIBRARY_NAME=nvidia
      - ROS_DOMAIN_ID=42
      - ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
      - RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
    volumes:
      - ..:/workspace
      - /tmp/.X11-unix:/tmp/.X11-unix:rw
      - ${XAUTHORITY}:/tmp/.docker.xauth:ro
      - gz-cache:/home/dev/.gz

volumes:
  gz-cache:
```

### 7.5. Подводные камни

- **Пробел в пути.** Каталог `bekai vision` содержит пробел, поэтому в Makefile
  все пути берём в кавычки. Внутри контейнера путь всегда `/workspace`.
- **Humble на хосте.** В контейнер не монтируем `.bashrc` и `.zshrc`, а
  `ROS_DOMAIN_ID=42` отделяет его узлы от хостовых.
- **Сеть хоста.** `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` не даёт роям выходить
  в локальную сеть.
- **Права на файлы.** UID контейнера совпадает с хостовым, сейчас это 1000.
- **Оба GPU.** Без offload окно Gazebo может уйти на AMD, поэтому проверяем
  рендерер внутри контейнера через `glxinfo`.
- **Fuel-кэш.** Монтируем `~/.gz` в именованный том, чтобы модели не скачивались
  после каждого запуска.

### Видео после каждой фазы

Фаза не считается завершённой, пока нет видео. Формат для LinkedIn:

- длительность 15–30 секунд;
- MP4 (H.264), квадрат 1080×1080;
- смысл понятен без звука: короткие подписи вшиты в кадр;
- первые 3 секунды показывают результат, в конце стоит логотип Bekai Vision;
- в кадре есть подпись «Simulation», показываем только то, что реально работает.

| Фаза | Что показывает видео |
| --- | --- |
| 0 | Одна команда запускает Gazebo в Docker на GPU |
| 1 | Три наземных робота едут независимо, в RViz видны их сенсоры |
| 2 | Роботы сами исследуют мир, общая карта растёт, виден процент покрытия |

- [ ] Адаптер дрона с тем же контрактом, что у наземного робота.
- [ ] Первая версия полёта: фиксированная высота, цели с той же карты.
- [ ] Совмещение карт воздух-земля (RQ3).
- [ ] Лёгкий режим дрона через плагин Gazebo без PX4, если ноутбук не тянет PX4.

**Готово, когда** 2 дрона и 3 наземных робота строят одну карту и находят людей.

### Фаза 6. Деградация связи (1–2 недели)

- [ ] Узел `comms_sim`: дальность, прямая видимость, полоса, потери, задержка.
- [ ] Весь обмен между роботами проходит только через него.
- [ ] Синхронизация при восстановлении связи.
- [ ] Сравнение разных уровней связи (RQ2).

**Готово, когда** робот без связи продолжает работу, а его данные попадают в общую
карту при восстановлении связи.

### Фаза 7. Эксперименты (1–2 недели)

- [ ] Замеры RTF, CPU, RAM и VRAM при 3, 4 и 5 роботах.
- [ ] Серийные запуски без окна: сценарий × `seed`, запись в `results/`.
- [ ] Сравнение составов роя (RQ1) и размеров (RQ4).
- [ ] Статистика по `seed`: среднее и разброс, а не один удачный запуск.

Симуляция идёт по `use_sim_time`, поэтому низкий RTF замедляет запуск, но не
отменяет его. Если 5 роботов работают слишком медленно, снижаем частоту сенсоров
и включаем лёгкий режим дронов.

### Фаза 8. Публикация (1 неделя)

- [ ] Итоговый ролик из видео фаз.
- [ ] Технический отчёт с честными ограничениями.
- [ ] Карточка на сайте с фактами, подтверждёнными владельцем.
- [ ] Выводы для будущего продукта.

## 9. Метрики

| Группа | Метрика |
| --- | --- |
| Покрытие | Процент площади во времени, время до 90% |
| Люди | Время до первого и последнего, полнота, точность, ошибка координат |
| Карта | ATE, ошибка относительно плана мира |
| Связь | Трафик на робота, задержка объединения карт |
| Система | RTF, CPU, RAM, VRAM |

## 10. Риски

| Риск | Что делаем |
| --- | --- |
| Не хватает ресурсов ноутбука | Рой до 5 роботов, замеры с Фазы 0, упрощённые сенсоры |
| Плохо совмещаются карты воздух-земля | Общая стартовая зона, виды под разными углами, отдельный результат для RQ3 |
| `mrg_slam` требует грубых начальных поз | Используем известную стартовую зону, проверяем в Фазе 4 |
| `mrg_slam` сложно провести через `comms_sim` | Проверяем в Фазе 4, запасной вариант: Swarm-SLAM |
| DDS нестабилен при многих узлах | Настраиваем Cyclone DDS, пробуем `rmw_zenoh` |
| `rmw_zenoh` не совместим с агентом PX4 | Для PX4 оставляем DDS или добавляем мост |
| Тепловая модель не применяется к анимированным `actor` | Используем статичные модели лежащих людей |
| YOLO плохо видит людей в Gazebo | Дообучаем на кадрах симуляции, тепловизор остаётся основным сигналом |
| Идеальный тепловизор завышает результаты | Добавляем шум, ложные источники и частичное перекрытие |
| Симуляция не переносится на реальный мир | Явно указываем это в отчёте |

## 11. Открытые решения

1. **Название.** `rescueswarm` является рабочим, его легко сменить сейчас.
2. **Лицензия.** Файла лицензии пока нет. Для открытой части с YOLO предлагается
   AGPL-3.0, как в AnchorAR. Решение нужно до публикации.
3. **GitHub.** Репозиторий пока только локальный. Предлагаемое имя:

## 12. Альтернативы на будущее

- **HERCULES.** Симулятор на Unreal Engine 5 для смешанных роев с LWIR-камерами.
  Он ближе к задаче по графике, но заметно тяжелее и на 6 GB VRAM не проверялся.
- **Lyrical + Jetty.** Переход при заметной выгоде или ближе к концу поддержки Jazzy.
- **10–15 роботов.** Только если исследованию понадобится больше 5, на отдельном
  сервере.
